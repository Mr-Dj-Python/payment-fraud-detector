## A real bug found and fixed during this chunk

`test_small_ring_is_caught_end_to_end_when_thresholds_are_met` **failed** on first
run: `rings_caught` was 0 when it should have been 1. Root cause: `detect()`
(Chunk 5) only checked hop-chain/near-cycle against the **receiver** of the current
transaction. In a forwarding leg (`mule -> cashout`), the account doing the
"received, then quickly forwarded" pass-through is the **sender** of that leg
(the mule), not its receiver — so the exact behavior hop-chain exists to catch was
never checked for. Fixed by checking both heuristics on both sender and receiver
stats, with a dedup guard so a reason code firing on both sides doesn't appear
twice in `reason_codes`. Full regression suite re-run after the fix — all 55 tests
pass, no prior test's exact-list assertions broke.

A second test (`test_ring_below_threshold_is_missed_end_to_end`) also failed on
the first post-fix run — but that one was a **flawed test**, not a code bug: it
only overrode `fan_out_threshold`/`fan_in_threshold`, leaving the default
2000ms hop-chain window in place, which (correctly, now that hop-chain checks
both sides) still caught the ring via the independent hop-chain signal. Fixed the
test to also push `hop_interval_ms` and `max_hop_chain_ms` past every heuristic's
threshold, not just two of four, so it actually tests "undetectable by this
detector" rather than "undetectable by two specific heuristics."
